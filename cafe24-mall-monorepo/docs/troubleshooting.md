# 기술적 문제 해결 사례

Cafe24라는 플랫폼 특유의 함정을 실측으로 좁혀 해결한 기록. 공통 패턴은 **"추정으로 우회하지 않고, 에러를 재현해 원인을 확정한 뒤 구조적으로 막는다"**.

## 1. 범용 FTP 배포 액션이 Cafe24에서 실패

- **증상**: 널리 쓰이는 GitHub Actions FTP 배포 액션이 Cafe24 FTP에서만 실패
- **원인**: 해당 액션이 내부적으로 쓰는 `CDUP`(상위 디렉토리 이동) 명령을 Cafe24 FTP 서버가 거부
- **해결**: lftp 기반 배포로 전환. 이후 모든 배포 워크플로의 공통 기반이 됨

## 2. phantom 파일 — 대소문자만 다른 중복 파일

- **증상**: 배포 후 특정 파일이 의도와 다른 내용으로 서빙됨. 로컬(macOS)에서는 아무 이상이 안 보임
- **원인**: Cafe24 default 스킨이 같은 파일을 대소문자 두 케이스로 배포(예: `Main.html` / `main.html`). 대소문자 비구분 파일시스템에서는 하나로 보여 발견 불가
- **해결**: 배포 전 게이트 스크립트가 대소문자 충돌을 검사해 차단, 의도된 예외는 allowlist로 관리

## 3. 봇 커밋이 후속 워크플로를 트리거하지 않음

- **증상**: 워크플로가 만든 커밋(봇 커밋) 뒤에 이어져야 할 배포 워크플로가 실행되지 않음
- **원인**: GitHub은 무한 루프 방지를 위해 기본 토큰으로 만든 커밋이 다른 워크플로를 트리거하지 않는 정책
- **해결**: 후속 워크플로를 API로 직접 호출하는 방식으로 우회

## 4. 운영 스킨 번호가 조용히 바뀜 (prod-skin drift)

- **증상**: 문서에 적어둔 운영 스킨 번호가 실제와 달라 잘못된 대상에 검증·배포할 뻔함
- **원인**: admin에서 스킨 복제·교체가 일어나면 번호가 바뀌는데, 문서의 사본은 갱신되지 않음
- **해결**: 스킨 번호를 문서에 복제하는 것 자체를 금지. 브랜드별 `mapping.yaml` 한 곳만 단일 진실로 두고 실행 시점에 읽는다 — "사본은 낡는다" 원칙의 출발점

## 5. 얕은 checkout에서 배포 기준 태그가 안 보임

- **증상**: promote가 diff 기준(직전 prod 태그)을 못 찾아 잘못된 기준으로 빠질 위험
- **원인**: CI의 shallow checkout에서는 태그 조회가 누락될 수 있음
- **해결**: 기준 결정 불가 시 자동 full 전환이 아니라 **사유를 출력하며 실패**하도록 설계하고, 태그 확인 절차를 promote 가이드에 명문화. "전체 덮어쓰기"는 항상 명시적 선택이어야 한다

## 6. admin 직접 수정과 저장소의 충돌

- **증상**: 운영에서 admin으로 직접 고친 파일을 다음 배포가 덮어써 수정이 증발할 위험
- **원인**: 코드 기준(저장소)과 실물(운영 스킨)의 이원화는 구조적으로 피할 수 없음
- **해결**: 3중 방어 — ①발생 시 import 워크플로로 즉시 흡수 ②잊어도 promote의 M-smart hash 대조가 충돌로 감지 ③충돌 시 배포 중단이 기본값, 강행은 명시적 bypass 입력 필요

# 기술스택과 선택 이유

| 기술 | 역할 | 왜 이걸 선택했나 |
|---|---|---|
| GitHub Actions | 배포·검증 파이프라인 | 상시 서버 없이 push 트리거·수동 dispatch·시크릿 관리까지 해결. 브랜드별 워크플로 분리로 변경 영향 범위를 브랜드 단위로 격리 |
| lftp | Cafe24 FTP 배포 | 범용 배포 액션(basic-ftp 기반)은 Cafe24 FTP가 `CDUP` 명령을 거부해 실패한다. 실측으로 원인을 좁힌 뒤 lftp로 전환 ([troubleshooting](./troubleshooting.md#1-범용-ftp-배포-액션이-cafe24에서-실패)) |
| Python | 가드 스크립트 | 배포 전 게이트(대소문자 충돌·drift·dead partial·스니펫 누락)를 CI에서 빠르게 실행 |
| Claude Code (스킬) | 자연어 요청 처리 | 반복되는 "배너 바꿔줘"류 요청을 AI가 처리하되, **브랜드별 스킬 문서로 절차(staging-first·검증 URL·recipe 학습)를 강제**. 자유로운 AI가 아니라 정해진 파이프라인 위의 AI |
| YAML (mapping.yaml) | 브랜드별 단일 진실 | 스킨번호·자연어 recipe·Figma 노드 매핑을 브랜드당 한 파일로. 문서에 사본을 두지 않고 실행 시점에 읽는다 |
| Google Apps Script | Slack 접수 다리 | 조직 정책상 커스텀 Slack 앱은 승인 대상. 내장 워크플로 빌더 + Sheets 커넥터 + GAS 트리거 조합으로 **승인 대기 0·상시 서버 0·비용 0**을 달성 ([설계](./slack-agent-pipeline.md)) |
| Figma + Tokens Studio | 디자인 시스템 | 색상·타이포·간격·모서리를 디자인 토큰으로 표준화해 디자인 도구와 코드의 기준을 일치 |
| 자체 도구 h2f | 라이브 페이지 → Figma | 운영 중인 실제 페이지를 노드 단위로 직렬화해 Figma로 재구성 — 디자인 시스템의 출발점을 "이상적 시안"이 아니라 "실물 화면"으로 |

## 선택의 공통 기준

1. **상시 인프라 최소화** — 서버를 띄우지 않고 GitHub Actions·GAS 같은 이벤트 기반 실행으로 해결
2. **실측 우선** — "안 된다"는 추정이 아니라 실제 에러를 재현·분석해 원인을 확정한 뒤 대안 선택
3. **AI는 절차 위에서** — AI 도입 시 자율성을 늘리는 게 아니라, 검증된 절차(staging-first·가드)를 스킬로 정의해 그 위에서만 움직이게 함

# 추적 데이터 정합성 사례

GA4와 GTM으로 수집되는 행동 데이터가 실제 거래와 맞는지 확인하고, 틀어진 곳을 코드에서 찾아 고친 두 사례. 브랜드명, 주문 정보, 컨테이너 ID, 스킨 번호, 외부 업체명은 전부 뺐다.

## 1. 구매 이벤트가 한 페이지에서만 통째로 빠져 있던 문제

### 발견

데이터팀이 한 브랜드의 보름치 실주문 수천 건이 GA4 purchase 이벤트에는 한 건도 없다고 알려 왔다. 같은 추적 설정을 쓰는 다른 브랜드들은 정상이었다. 즉 설정 문제가 아니라 그 브랜드의 스킨 코드 문제였다.

### 원인

카페24 스킨에서 GA4와 픽셀 추적 블록은 한 파일에 모여 있고, 공통 하단 레이아웃이 그 파일을 불러오는 구조였다. 그런데 이 브랜드의 주문완료 페이지는 공통 레이아웃을 쓰지 않는 독립 페이지였다. 하단이 붙지 않으니 추적 블록도 따라오지 않았고, 파일 안에 직접 불러오는 줄도 없었다. 저장소에 처음 들어온 시점부터 그랬으므로 추적 설치 이후 내내 누락돼 있던 것이다. 정상인 다른 브랜드들은 주문완료 파일 끝에 불러오는 줄을 직접 두고 있었다.

메인과 장바구니에는 추적이 있어서 일반 페이지뷰는 정상으로 보였다. 구매 단계에서만 빠지는 누락은 전체 수치를 봐서는 안 보이고, 주문 건수와 purchase 건수를 맞춰 봐야 드러난다.

### 수정

- 정상 브랜드와 같은 방식으로 주문완료 페이지 끝에 추적 블록을 불러오는 줄을 넣었다.
- 개발 스킨에 배포하고, 운영 스킨 파일을 받아 해시를 대조해 이번에 바뀌는 파일이 하나뿐인지 확인한 뒤 운영에 반영했다.
- 데이터팀의 요청 항목 중 "GA4 블록만 분리해 넣을 수 있나"는 불가로 답했다. GA4 블록이 앞 픽셀 블록의 변수를 참조하므로 한 줄로 함께 들어가야 했다.

### 검증

주문완료 화면은 결제 없이는 열리지 않아 코드만으로는 확인이 끝나지 않는다. 가상계좌 테스트 주문을 넣고 브라우저로 확인했다.

- 추적 스크립트 로드 확인
- dataLayer에 거래 ID, 결제 금액, 배송비, 품목 수가 실리는지 확인
- GA4 수집 요청에 purchase 이벤트가 실제로 송신되는지 네트워크에서 확인

같은 검사에서 주문서 페이지도 추적이 없어 begin_checkout이 빠지는 것을 발견했다. 다른 브랜드들은 주문서에도 불러오는 줄이 있었으므로 같은 위치에 추가하고, 주문서를 열어 dataLayer와 begin_checkout 송신을 확인했다. 페이지뷰와 함께 2건이 찍히는 것은 스트림이 둘이라서이고 중복이 아니었다.

### 교훈

- 추적 코드가 "공통 레이아웃에 있으니 전 페이지에 들어간다"는 가정은 독립 페이지에서 깨진다. 거래 단계 페이지는 따로 확인해야 한다.
- 설치 여부는 페이지뷰 총량이 아니라 거래 건수 대비 이벤트 건수로 본다.
- 수정 검증은 실제 거래 한 건으로 끝까지 한다. 코드 diff와 파일 해시는 반영 여부를 말해 줄 뿐 이벤트가 나가는지는 말해 주지 않는다.

## 2. 체류 0초 유입을 만들던 외부 추적 스크립트

### 발견

마케팅팀이 GA4 BigQuery 데이터에서 체류 0초 세션이 특정 유입 소스로 꾸준히 잡히는 것을 발견했다. 전체 상품 페이지뷰의 일부가 이 패턴이었고, 특정 두 브랜드에서만 나타났다. 그 두 브랜드에는 외부 광고 매체의 전환추적 스크립트가 설치돼 있었다.

### 분석

- 스크립트 본문을 읽었다. 상품 페이지에서 보이지 않는 iframe을 만들어 외부 도메인을 호출하고, 그 안에서 자사 상품 페이지를 광고 유입 파라미터가 붙은 주소로 다시 불러오고 있었다. 이 재로드가 GA4와 쇼핑몰 자체 분석 도구에 체류 0초 방문으로 기록됐다.
- 처음에는 평문 검색으로 호출 도메인을 찾지 못했다. 주소가 base64로 인코딩돼 있었기 때문이다. 디코드해서 호출 도메인과 하위 스크립트를 확인했고, 이 하위 스크립트가 브라우저 지문을 수집하는 계열임을 확인했다. 외부 스크립트를 분석할 때 인코딩된 문자열은 반드시 디코드해야 한다는 것을 이 과정에서 배웠다.
- 설치 범위를 전수로 확인했다. 저장소 전체 검색, 13개 몰의 운영 메인과 상세 페이지 렌더 결과, 10개 GTM 컨테이너 본문을 검색해 해당 스크립트가 두 브랜드의 스킨 블록에만 있고 관리자 공통 영역이나 GTM을 통해 들어온 것은 아님을 확인했다.

### 제거

- 두 브랜드의 스킨 파일에서 해당 블록을 삭제했다. 삭제만 하고 추가는 없었고, script 태그 열림과 닫힘 개수가 기존과 같음을 확인했다.
- 한 브랜드는 주문완료 파일의 운영본이 저장소의 어느 커밋과도 일치하지 않았다. 관리자 화면에서 직접 수정된 흔적이었다. 안전 검사가 충돌로 막는 것이 맞았고, 사용자 승인 아래 그 파일만 별도로 반영했다.

### 검증

- 개발과 운영 양쪽에서 메인, 목록, 상세, 가입, 장바구니 페이지를 렌더해 스크립트 흔적 0건을 확인했다.
- 브라우저 자동화로 메인, 상세, 장바구니를 열고 스크롤하면서 해당 도메인으로 나가는 네트워크 요청이 0건인지, 스크립트가 만들던 전역 변수가 없는지 확인했다.
- 제거 이후 GA4에서 그 유입 소스의 신규 세션이 0이 되는지는 마케팅팀이 확인하는 최종 지표로 넘겼다.

### 한계로 남긴 것

- 이미 방문자 브라우저에 심긴 쿠키는 만료될 때까지 남는다.
- 외부 업체 서버 쪽 데이터와 광고 소재 안의 스크립트는 우리가 지울 수 없다.
- 전환 수집이 끊기는 것은 광고 집행 쪽 영향이므로 미디어팀 인지 여부를 확인하도록 넘겼다.

## 두 사례의 공통점

둘 다 수집 설정을 새로 만든 일이 아니라, 이미 돌고 있는 수집이 실제와 맞는지 확인하고 틀어진 지점을 코드에서 찾은 일이다. 발견은 데이터를 보는 팀이 했고, 원인 규명과 수정, 검증은 화면 코드를 관리하는 쪽에서 했다. 화면을 만드는 사람이 수집까지 같이 보면 이런 누락과 오염을 더 일찍 잡을 수 있다.

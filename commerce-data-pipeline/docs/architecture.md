# 시스템 아키텍처

## 계층 구조

```
[판매 채널 셀러 센터]
        │
  수집 계층 — 실제 브라우저 + 계정별 영속 프로필 + 사람 유사 입력
        │
  ┌─────┼──────────────────────┐
  ▼     ▼                      ▼
 시간별 수집          일배치 (T-1 확정치)      당일 시간별 스냅샷
 → Google Sheets     → BigQuery              → BigQuery intraday
 (매출팀 공유)        (append-only + CDC)     (매시간 통째 교체)
                          │
                     서버팀 silver 계층 (중복 제거·신선도 모니터링·최신값 수렴)
```

- **공용 기반 모듈** — 로그인·봇 우회·사람 입력·시트 기록·실패 로그·Slack 전송을 하나의 기반 모듈이 제공하고, 모든 진입점이 이를 import해 재사용
- **진입점 분리** — 시간별 수집 / 일배치 / 당일 스냅샷 / 목적별 성과 수집이 각각 독립 진입점. 하나가 죽어도 나머지는 돈다

## 적재 설계 — append-only + CDC

광고 전환 성과는 며칠 뒤에 확정된다(늦게 도착하는 데이터). 이를 UPDATE로 풀지 않고:

1. 매일 **최근 N일을 통째로 재적재** (append-only — 원본 테이블엔 같은 날짜의 세대가 쌓임)
2. 하류(silver)에서 **최신 세대로 수렴** — 중복 제거·신선도 모니터링은 소비 시점에

이 구조의 장점: 적재가 멱등에 가깝고(재실행해도 안전), 원본에 이력이 남고, 적재용 서비스 계정을 **insert 전용(SELECT 불가)** 최소 권한으로 만들 수 있다.

## 모니터링 — 두 층 + 자동진단

| 층 | 감지 대상 | 채널 |
|---|---|---|
| 실행 실패 | 예외·타임아웃·로그인 실패 | Slack 실패 요약 DM |
| 적재값 이상 | 브랜드 누락·파싱 의심·급락·신선도 | Slack 이상탐지 다이제스트 DM |
| 자동진단 | 위 실패 알림의 **원인** | AI 진단 결과 DM ([설계](./auto-diagnosis-bot.md)) |

"예외로 죽는 실패"보다 "예외 없이 틀린 숫자가 들어가는 실패"가 더 위험하다는 전제로, 값 이상 감지를 실행 실패와 동급의 감시 대상으로 뒀다.

## 게이트 — fail-closed

수집값이 의심스러우면 적재를 막는 쪽으로 실패한다(fail-closed). 예: 캠페인 비용이 일 예산의 배수를 초과하면 "누적 테이블을 잘못 읽었다"는 신호로 보고 적재를 차단. 틀린 값이 조용히 들어가는 것보다 수집이 한 번 빠지는 쪽이 싸다.

## 배포·운영

```
개발 머신:  수정 → git commit → push
운영 머신:  git pull  (Windows 작업 스케줄러가 배치 진입점 실행)
```

- 비밀값(.env)·세션 프로필·데이터·로그는 전부 gitignore — pull해도 유지
- 배치 파일은 `.gitattributes`로 CRLF 자동 정규화 (수동 복사 배포 시절의 줄바꿈 깨짐 원천 차단)

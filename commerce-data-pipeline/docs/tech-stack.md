# 기술스택과 선택 이유

| 기술 | 역할 | 왜 이걸 선택했나 |
|---|---|---|
| Python | 전체 파이프라인 | 브라우저 자동화·API 연동·BigQuery 클라이언트를 한 언어로. 운영 머신(Windows)에서 의존성 최소로 구동 |
| Patchright (실브라우저 자동화) | 봇 차단 채널 수집 | JS 스텔스 라이브러리로는 TLS 지문·CDP 누수·센서 쿠키 탐지를 못 넘긴다. **실제 브라우저 + 계정별 영속 프로필**로 신뢰 누적(2FA 트러스트 포함)을 재사용하고, 로그인은 만료됐을 때만(reactive) 수행 |
| 공식 정산 API | API 제공 채널 | 제공되는 채널은 크롤링하지 않고 판매자 본인 애플리케이션을 등록해 정식 연동 — 채널별로 가장 안정적인 경로 선택 |
| BigQuery | 누적 분석 저장소 | 시트만으로는 분석·정산·타팀 공유가 어렵다. append-only + CDC로 늦게 확정되는 값을 흡수 ([architecture](./architecture.md#적재-설계--append-only--cdc)) |
| Google Sheets API | 매출팀 실시간 공유 | 소비자가 비개발자(매출팀) — 그들이 이미 쓰는 도구에 적재 |
| Slack 워크플로 웹훅 | 알림·진단 DM | 커스텀 앱 승인이 필요 없는 내장 워크플로 웹훅으로 알림 전송. 실패·이상탐지·진단용 웹훅을 각각 분리 |
| Claude Code (헤드리스) | 실패 자동진단 | 실패 원인 조사는 "로그 읽고 → 코드 찾고 → 가설 검증"의 반복 — 사람이 하던 이 루프를 AI에 위임하되, 격리 환경 + 읽기 전용 권한으로 가둠 ([설계](./auto-diagnosis-bot.md)) |
| git (배포) | 개발→운영 배포 | 수동 파일 복사의 취약함(줄바꿈 깨짐·파일 엇갈림·이력 부재)을 push/pull로 통일 |

## 선택의 공통 기준

1. **채널마다 가장 안정적인 경로** — API가 있으면 API, 없으면 실브라우저. 하나의 방식을 고집하지 않음
2. **틀린 값 방지 > 수집 성공률** — fail-closed 게이트, insert 전용 최소 권한, 다층 검증
3. **운영 머신은 단순하게** — 상시 서비스 없이 작업 스케줄러 + git pull로 운영, 상태·비밀은 전부 로컬 파일

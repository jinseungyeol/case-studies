# 기술적 문제 해결 사례

## 1. 위치 기반 식별의 붕괴 → URL 기준 전환

- **증상**: 본문에 이미지가 하나 삽입되면 그 뒤의 모든 자산 매핑이 한 칸씩 밀림
- **원인**: 자산을 "본문의 N번째 이미지"로 식별하는 위치 기반 설계의 구조적 한계
- **해결**: 식별 기준을 URL로 전환. 위치는 부가 정보로 강등하고 매일 드리프트 스캔이 재매핑. 이후 "URL이 같은데 내용이 바뀌는" 사각지대는 ETag 스윕으로 보완 — 식별 체계를 두 겹(URL + 내용 지문)으로

## 2. 본문을 고치면 에디터가 깨짐 → 본문 write 경로 자체를 제거

- **증상**: 본문 HTML을 프로그램이 수정하면 플랫폼 에디터와의 호환이 깨지고 원복 불가
- **해결**: "조심해서 고친다"가 아니라 **고치는 코드를 없앴다**. 서빙 시점에 브라우저에서 교체하는 clean-body 구조로 전환. 부수 효과로 API 권한이 읽기 전용 단일 scope로 축소
- **교훈**: 위험한 연산은 가드로 감싸는 것보다 존재하지 않게 만드는 것이 확실하다

## 3. 스니펫 위치에 따른 선점 실패

- **증상**: 스니펫이 이미지 로드보다 늦게 실행되면 원본이 먼저 전송됨
- **해결**: head 최상단 **동기** 스니펫으로 로드 선점을 보장하고, 원본 요청이 전송 전 취소되는지(ERR_ABORTED, 전송량 0KB)를 브라우저 실측으로 확인

## 4. 워커 사망으로 잔류하는 "변환 중" 고아

- **증상**: 워커가 OOM 등으로 죽으면 작업이 "변환 중" 상태로 영구 잔류 — 해당 자산은 원본 폴백만 계속됨 (화면은 정상이라 발견이 늦음)
- **해결**: 리퍼가 주기적으로 오래된 진행 중 상태를 회수해 재큐잉. "candidates=0이어도 로그 1줄"을 남겨 리퍼 자체의 생존을 확인 가능하게 — 감시자를 감시하는 장치

## 5. 제자리 교체 시 유니크 제약 충돌

- **증상**: 같은 위치에 새 이미지를 교체하면 orphan 처리와 신규 등록이 유니크 제약에서 충돌
- **해결**: orphan을 삭제하지 않고 톰스톤 식별자로 이동시키는 소프트 마킹 — 이력 보존과 제약 회피를 동시에

## 6. 자체 도메인 몰의 ETag 부재

- **증상**: 일부 몰(자체 도메인)은 CDN ETag가 없어 내용 변경 감지 불가
- **대응**: 해당 경로는 커버 범위 밖임을 **명시적으로 수용하고 문서화**, 개선 후보로 기록. 모르는 척이 아니라 아는 구멍으로 관리

# 기술스택과 선택 이유

| 기술 | 역할 | 왜 이걸 선택했나 |
|---|---|---|
| NestJS | 백엔드 (스캔·변환·서빙·스캐줄) | 모듈 구조로 스캔/변환/서빙/드리프트 스캔을 도메인별로 분리, DI로 저장소·큐 구현 교체 용이 |
| Next.js | 관리자 UI | 운영 상태 대시보드·수동 제어(재압축·롤백)를 빠르게 구축 |
| PostgreSQL + Prisma | 장부 DB | 위치·내용 장부의 관계와 유니크 제약(중복 등록 차단)을 스키마 수준에서 강제 |
| pg-boss | 변환 작업 큐 | 별도 브로커(Redis 등) 없이 PostgreSQL 위에서 작업 큐·재시도·스케줄을 해결 — 인프라 최소화. DB 트랜잭션과 큐가 같은 저장소라 상태 일관성 관리가 단순 |
| sharp | WebP 변환 | 검증된 고성능 이미지 변환. 변환 파라미터를 자산 유형별로 조정 |
| GCS (비공개 버킷) | 변환본 저장 | 해시 주소(content-addressed) 저장으로 dedup이 구조적으로 보장. 서빙은 게이트웨이 뒤에서만 |
| CDN | WebP 서빙 | 게이트웨이 응답을 캐시. 원본 CDN의 ETag(=콘텐츠 MD5, 실측 확인)는 변경 감지 지문으로도 활용 |
| Cafe24 API (읽기 전용) | 본문 스캔 | 무오염 구조 덕에 쓰기 권한 자체가 불필요 — 단일 read scope로 최소 권한 |

## 선택의 공통 기준

1. **되돌릴 수 있는가** — 모든 선택의 첫 질문. 본문 불가침·상태 스위치·302 폴백 모두 "즉시 원복"이 기준
2. **인프라 최소화** — 큐도 DB 위에(pg-boss), 저장은 관리형(GCS) — 운영 부담을 앱 하나로 수렴
3. **실측 기반** — ERR_ABORTED 전송량 0, ETag=MD5, 롤백 시 본문 PUT 0회 등 핵심 가정을 전부 실측으로 확인 후 채택

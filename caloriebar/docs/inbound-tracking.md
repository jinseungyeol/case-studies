# 광고 유입 파라미터 수집 구조

TV홈쇼핑과 온라인 광고로 들어온 체험 예약이 어느 광고에서 왔는지 알 수 있도록, 유입 파라미터를 받아 예약 데이터에 붙이는 구조. 방문자 집계 미들웨어와는 별개의 미들웨어다.

## 문제

예약은 랜딩 페이지에 들어온 뒤 몇 페이지를 거쳐 신청 폼에서 생긴다. 광고 링크에 붙은 utm 파라미터는 첫 페이지 주소에만 있고, 신청 폼을 제출하는 시점에는 이미 주소에서 사라져 있다. 그래서 신청 폼의 값만 저장하면 예약과 광고를 연결할 수 없었다.

## 구조

```
광고 링크 (utm_*, n_* 붙은 주소)
      │
  유입 파라미터 미들웨어: GET 요청에 대상 파라미터가 하나라도 있으면 세트 전체를 세션에 저장
      │
  페이지 이동 (주소에는 파라미터 없음, 세션에는 남아 있음)
      │
  예약 생성 뷰: 세션의 파라미터 세트를 꺼내 예약 레코드의 유입 필드에 저장
      │
  백오피스: 예약별 유입 소스, 매체, 캠페인, 검색어 확인
```

- 수집 대상은 표준 utm 5종(source, medium, campaign, term, content)과 네이버 검색광고가 자동으로 붙이는 파라미터 4종(검색어, 등록 키워드, 순위, 광고그룹)이다. 네이버 파라미터는 utm과 한 세트로 취급한다.
- 저장 방식은 last-touch다. 대상 파라미터가 하나라도 오면 세트 전체를 덮어쓰고, 없는 키는 공란으로 둔다. 광고를 두 번 타고 들어오면 마지막 광고가 남는다.
- 값은 공백을 제거하고 길이를 제한해 저장한다. 미들웨어 안의 예외는 전부 잡아서 로그만 남긴다. 유입 추적이 실패해도 페이지 응답은 영향을 받지 않아야 하기 때문이다.
- 예약 모델에는 같은 이름의 필드 9개가 있고, 예약을 만드는 뷰가 세션에서 세트를 꺼내 그대로 채운다. 세션에 아무것도 없으면 전부 공란이다.

## 설계에서 정한 것

- 왜 세션인가. 쿠키에 직접 쓰면 값이 클라이언트에 노출되고 길이 제한에 걸린다. 세션은 서버에 있고 페이지를 몇 번 거쳐도 유지된다.
- 왜 last-touch인가. 예약 한 건을 어느 광고에 귀속할지는 마케팅 쪽 결정이었고, 마지막 유입을 기준으로 삼기로 했다. first-touch가 필요해지면 세션에 첫 세트를 따로 두면 된다.
- 왜 네이버 파라미터를 같이 받나. 네이버 검색광고는 utm과 별도로 자기 파라미터를 붙인다. 이것을 안 받으면 검색어 단위 성과를 볼 수 없다.
- 왜 방문자 집계와 분리했나. 방문자 집계는 IP와 시간 단위로 중복을 제거하는 쓰기 작업이고, 유입 파라미터는 세션에 값을 두는 읽기 작업에 가깝다. 책임이 달라 미들웨어를 나눴다.

## 확인 방법

- 광고 링크 형태의 주소로 들어와 페이지를 옮긴 뒤 신청하면 백오피스 예약 상세에 유입 값이 붙는다.
- 파라미터 없이 들어와 신청하면 유입 필드가 전부 공란이다.
- 두 광고를 연달아 타면 두 번째 광고 값만 남는다.

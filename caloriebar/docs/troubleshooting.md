# 기술적 문제 해결 사례

## 1. 신규 채널 추가 시 기존 신청 데이터 무손실 보존

- **상황**: 단일 홈쇼핑 채널 전제로 만들어진 신청 시스템에 신규 채널을 추가해야 함. 기존 신청 데이터는 채널 구분 없이 한 테이블에 쌓여 있었음
- **접근**: 별도 테이블 신설 대신 신청 모델에 `channel` 컬럼(CharField·choices, `default`=기존 채널)을 추가. 디폴트값 덕분에 기존 행이 마이그레이션 시 자동으로 기존 채널로 분류됨. 배포 전 DB 백업 → 마이그레이션 → 건수 대조로 무손실 검증
- **결과**: 두 채널을 단일 테이블 + 채널 컬럼으로 독립 운영. 신청 로직은 공용 폼 함수를 채널별로 래핑해 재사용(다만 채널 추가 자체는 choices·뷰·URL·매장 데이터 변경을 수반)

## 2. 방문자 통계의 중복 부풀림

- **증상**: 새로고침·재방문이 방문 수를 부풀림
- **해결**: 집계 시점에 걸러내는 로직 대신 **IP+시간 단위 유니크 제약**을 DB에 둠 — 중복 삽입 자체가 실패하므로 애플리케이션 로직의 누락·경합에 영향받지 않음

## 3. 개발 중 운영 DB 오염 위험

- **상황**: 소규모 팀에서 로컬 개발과 운영 DB 설정이 섞이면 사고가 남
- **해결**: 환경 변수 하나로 로컬은 빈 SQLite 구동. 운영 자격증명이 로컬 기본 설정에 존재하지 않아 실수 경로 원천 차단

## 4. 회차 운영의 수작업 제거

- **증상**: 방송 일정마다 신청 폼을 새로 만들거나 분기 로직을 손대는 반복 작업
- **해결**: 신청 가능 차수를 뷰의 허용 리스트(`active_rounds`)로 분리 — 방송 오픈/마감이 리스트 한 줄 변경으로 끝남(허용 밖 차수 접근은 404). 폼 자체를 새로 만들 필요가 없어짐
